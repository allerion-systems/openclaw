# Allerion: Website-Installable Distribution of OpenClaw

Design for shipping "Allerion" — the allerion-systems app built on this OpenClaw fork — as a
product users install by downloading from the Allerion website (allerion.io), instead of
installing from openclaw.ai or npm.

## Context

- allerion-systems already runs a live OpenClaw gateway + Control UI at `jolly.allerion.io`
  (currently on 2026.6.11, matching this fork).
- The goal is a first-party install experience: a user visits the Allerion website, clicks
  Download, and gets a working app — the same runtime as OpenClaw (gateway, channels,
  plugins, Control UI, companion apps), branded and distributed by Allerion.
- OpenClaw is MIT-licensed, so redistribution and rebranding are permitted provided the
  `LICENSE` and `THIRD_PARTY_NOTICES.md` files ship with every artifact. The OpenClaw
  name/logo should not be used as Allerion's brand (trademark hygiene); "built on OpenClaw"
  attribution is fine and honest.

## Guiding decision: distribution brand, not source rename

Do **not** rename `openclaw` throughout the source tree. A full rename (~binary name, config
dir, env vars, package ids) would touch thousands of files and make every upstream sync a
merge war. Instead, follow the Chromium→Chrome / VS Code→VSCodium model:

- The **runtime stays `openclaw`** (CLI name, `~/.openclaw` config dir, plugin/SDK ids).
  Upstream merges stay cheap; ClawHub plugins keep working unmodified.
- **Allerion is the distribution layer**: the website, the installers, the download
  artifacts, the macOS app branding, the update feed, and the default config it ships
  (e.g. gateway preconfigured the way allerion-systems wants).
- Rebrand surface is limited to things a downloading user sees: installer names, DMG/app
  name and icon, website copy, appcast title, docs links.

If a deeper rename is ever wanted, it becomes a separate, explicit project — not a
prerequisite for shipping downloads.

## What already exists (reuse, don't rebuild)

| Need | Existing OpenClaw machinery | Where |
| --- | --- | --- |
| Website install scripts | `install.sh`, `install-cli.sh`, `install.ps1` served from openclaw.ai | sibling `openclaw.ai` repo; internals documented in `docs/install/installer.md` |
| macOS app packaging | `pnpm mac:package` | `scripts/package-mac-app.sh`, `apps/macos/` |
| macOS auto-update | Sparkle feed | `appcast.xml` (repo root, referenced by the Mac app) |
| CLI runtime install without root | local-prefix Node + npm install into `~/.openclaw` | `install-cli.sh` mode |
| Release build pipeline | `pnpm build:ci-artifacts`, `release:*` scripts | `package.json`, `scripts/` |
| Mobile apps | iOS/Android release scripts | `apps/ios`, `apps/android`, `ios:release:*`, `android:release:*` |

The new work is almost entirely: fork the installer-site repo, host artifacts under
allerion.io, and repoint the update/install URLs.

## Architecture

### 1. Artifact set (what "Download" gives you)

| Platform | Primary artifact | Notes |
| --- | --- | --- |
| macOS | `Allerion.dmg` — signed + notarized app | Built by `package-mac-app.sh` with Allerion name/icon/bundle id (`io.allerion.app`); embeds/manages the openclaw runtime as today; Sparkle auto-update pointed at `https://allerion.io/appcast.xml` |
| Windows | `AllerionSetup.exe` (or `iwr allerion.io/install.ps1 \| iex`) | Phase 1: serve `install.ps1` (fork). Phase 2: NSIS wrapper that runs the same logic with a GUI — no new install machinery, just packaging |
| Linux / WSL / macOS CLI-only | `curl -fsSL https://allerion.io/install.sh \| bash` + downloadable tarball | Fork of the openclaw.ai scripts with Allerion URLs; tarball = the npm pack output + pinned Node, same layout `install-cli.sh` produces in `~/.openclaw` |
| iOS / Android | App Store / Play (or TestFlight/APK from the site) | Existing `ios:release:*` / `android:release:*` pipelines; stores are the realistic distribution channel, the website links to them |

Every downloadable artifact page publishes SHA-256 checksums and a minisign (or GPG)
signature, generated by the release pipeline.

### 2. Hosting layout (allerion.io)

```
allerion.io/
  download            → download page (platform-detected buttons)
  install.sh          → forked installer (Allerion defaults)
  install-cli.sh      → forked local-prefix installer
  install.ps1         → forked Windows installer
  appcast.xml         → Sparkle feed for the Mac app
  releases/
    <version>/Allerion-<version>.dmg
    <version>/allerion-cli-<version>-<os>-<arch>.tar.gz
    <version>/SHA256SUMS + SHA256SUMS.minisig
jolly.allerion.io     → existing hosted gateway (unchanged; the website links to it as the "hosted" option)
```

Static hosting + object storage (e.g. Cloudflare Pages/R2, same shape as OpenClaw's docs
flow) is sufficient; no server-side logic is needed for distribution.

### 3. Release pipeline (fork CI)

One GitHub Actions workflow in this fork, `release-allerion.yml`, triggered by tag:

1. `pnpm install && pnpm build` (+ `pnpm build:ci-artifacts`).
2. `pnpm mac:package` with Allerion signing identity → notarize → staple → DMG.
3. `npm pack` + pinned Node → per-OS/arch CLI tarballs.
4. Generate `SHA256SUMS`, sign with minisign key (CI secret).
5. Upload artifacts to `allerion.io/releases/<version>/` (R2/S3 bucket).
6. Regenerate `appcast.xml` (new `<item>` with version, pubDate, enclosure URL, EdDSA
   signature) and deploy it + the download page.

Versioning: track upstream (`YYYY.M.PATCH`), optionally suffixed `+allerion.N` for
fork-only respins. Secrets required: Apple Developer ID cert + notarization key,
minisign private key, bucket credentials. (Windows Authenticode cert only when the Phase-2
NSIS installer lands.)

### 4. Update story

- **Mac app**: Sparkle checks `allerion.io/appcast.xml` (one URL constant in
  `apps/macos` + the packaging script). Users get in-app updates automatically.
- **CLI installs**: the forked `install.sh` doubles as the updater (idempotent re-run),
  matching OpenClaw's documented `docs/install/updating.md` flow but against Allerion URLs.
- **Hosted gateway** (`jolly.allerion.io`): redeployed by the same pipeline so hosted and
  downloaded versions stay in lockstep.

### 5. Upstream sync strategy

- Keep this fork rebased on `openclaw/openclaw` main (or ride release tags).
- All Allerion-specific state lives in a small, enumerable set: the CI workflow, the
  packaging-script branding variables, the appcast URL constant, and the separate
  website/installer repo (`allerion.io`, forked from `openclaw.ai`). Target: **< ~10 files
  diverged in this repo**, so every upstream merge is near-clean.

## Changes required (by repo)

**This repo (allerion-systems/openclaw):**
- `scripts/package-mac-app.sh` + `apps/macos` packaging metadata: parameterize app name,
  bundle id, icon, and appcast URL (env-driven so upstream default remains OpenClaw).
- `.github/workflows/release-allerion.yml`: the pipeline above (new file, no upstream conflict).
- `appcast.xml`: not reused — Allerion's feed is generated into the website bucket; this
  file stays upstream-owned.

**New repo `allerion-systems/allerion.io`** (fork of `openclaw.ai`):
- Rebrand installer scripts' product URLs/names; keep flags and behavior identical so
  `docs/install/installer.md` semantics still hold.
- Download page with platform detection, checksums, release notes.

**No changes** to core `src/`, plugins, gateway protocol, or config surface — the runtime
is untouched, which is what keeps this maintainable.

## Legal checklist (ships with every artifact)

- `LICENSE` (MIT, OpenClaw Foundation copyright) and `THIRD_PARTY_NOTICES.md` included in
  DMG, tarballs, and installer output.
- Website credits "built on OpenClaw" with a link; Allerion branding contains no OpenClaw
  marks.
- Mobile store listings follow the same attribution rule.

## Phasing

1. **Phase 1 — CLI download (days):** fork `openclaw.ai` → `allerion.io`, repoint URLs,
   publish install scripts + tarballs + checksums, download page live. Users can install
   from the website on macOS/Linux/Windows(PowerShell).
2. **Phase 2 — Mac app (1–2 weeks):** Apple Developer ID, parameterized `mac:package`,
   notarized DMG, Sparkle feed on allerion.io, in-app updates.
3. **Phase 3 — Windows GUI installer + mobile:** NSIS wrapper around install.ps1 logic;
   iOS/Android via the existing release scripts to the stores.

## Verification

- Fresh-machine (VM/container) runs of `curl allerion.io/install.sh | bash`,
  `install-cli.sh`, and `install.ps1` → `openclaw --version` works, onboarding starts.
- DMG: install on a clean macOS user account, verify Gatekeeper passes (notarization),
  Sparkle sees an update when appcast advances.
- Checksums/signature verification documented on the download page and tested in CI.
- Upstream-merge drill: merge a newer openclaw main into the fork and confirm the
  Allerion-diverged file set is still the enumerated short list.
